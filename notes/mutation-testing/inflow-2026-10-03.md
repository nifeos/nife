# Inflow, measured: the survivors merged pull requests added on their own lines

Lane `risk3-inflow`, 2026-10-03 (UTC). This appendix of [notes/mutation-testing.md](../mutation-testing.md)
answers what fatal risk 3's ruled condition asks (calef, 2026-09-20): are the survivors a merged pull
request adds on its own lines triaged? It reads the artifacts of two scheduled-workflow runs; no
mutation sweep was run for it. Verdicts, colors and ordering are calef's, and none is written here.

## The premise to correct first

Milestone 517 (what fraction of survivor growth arrives on lines a pull request touched) is a **one-off measurement, not a weekly
report**. It blamed the 2026-09-14 census once and replayed six commits. Nothing in
`.github/workflows/mutation.yml`, `script/mutation` or `script/mutation-census` computes inflow, and
`grep -n "in-diff\|blame"` over them finds only a comment. So 517 has reported nothing each week.
Milestone 438 (would a diff-scoped mutation check have caught the 55, and what would it cost) measured `--in-diff` by replay; the recipe lives in a note and no step runs it. The weekly job reports
per-crate totals only.

## 3. Is anything making sure inflow is triaged?

No. The census workflow writes a step summary of per-crate totals; nobody is paged by it, it failed
on 2026-09-28 and the next report came from a manual dispatch, and `notes/project-metrics/mutation-census.csv`
stops at 2026-09-21 (capture is a manual `script/mutation-census --add-run`). The triage that did happen
is milestone 637, a lane started by a person reading the census. That is rung 4 (a report) at best,
and in practice rung zero, "somebody will notice". The 10-03 artifacts expire about 2026-12-31.

## 4. Recommendation: smallest mechanism

A rung 2 check, inside the existing weekly workflow, no new gate on merges (milestone 479 (a blocking `--in-diff` mutation gate) stays refused):

1. One committed file, `notes/project-metrics/mutation-triage.csv`: `crate,function,mutation,disposition,reason`,
   one row per triaged survivor. The ledgers already hold this information in prose; the file is the
   same fact in a form a script can read.
2. One step after the aggregate in `mutation.yml` that diffs the run against the previous census row set,
   blames the new survivors, and fails the job listing any inflow survivor with no triage row. A red
   scheduled job is what `script/cadence-check` exists to read; whether it would page anyone is not checked here.
3. The same step appends the run to `mutation-census.csv`, so capture stops depending on memory.

Cost: one script, one workflow step, one CSV. Unpriced: the blame step needs full history in the job,
and the backfill of the roughly 630 dispositions in the 10-03 ledgers from prose. If no row-level file is wanted, the cheaper
and weaker form is step 3 plus the step-2 count printed to the summary (rung 4, not rung 2).
Would we choose it at equal effort? Yes; the file is the part that makes "triaged" checkable. This is
a recommendation and not built; the name of the script and file are provisional and calef's to ratify.

What the work found, beyond the rows.

- A rung-1 answer beat a test twice. `abi::fault::FAULT_EP_SLOT` is "the last slot" by its
  documentation and `CAPABILITY_TABLE_SLOTS - 1` by its text, and a wrong operator compiled; a const
  assert makes it not compile. `subtree_scope` and `slabtop` needed tests because their wrong states
  are values.
- The test that asserts the written byte does not see the store width. `screen_console`'s
  `copy_wide` lands the same bytes whatever alignment its qword stores have, so four mutants of the
  alignment arithmetic survived a byte-for-byte test. The new test asserts the address, which is the
  property the wide path exists for.
- `timetable::range` and `device_tree_blob` each had a bound only the constant's own spelling
  tested. A step of 60 through the minute branch and `h <= 24` both set hour bits past the day
  for an end past midnight; the new test holds the mask to 24 bits for every step form.
- `write_right` is copied into `free`, `vmstat` and `slabtop`. The proposal
  `design/roadmap/0793-one-crate-for-the-copied-right-aligned-number-writer.md` holds it; the
  crate name is calef's.
- Four survivors outside the list appeared on re-run. A new test kills both
  `memory_regions::RegionTable::return_to_parent` mutants. The two `uefi_loader` `output_len`
  mutants are argued equivalent, because that bound is deliberately generous. All four have rows
  marked as found on re-run.
- The fixture `crates/jh7110_clock_and_reset/tests/fixtures/jh7110-pmic-bus-overfull.dts` (and
  its `.dtb`) is new and its name is provisional.

Left: 215 keys by the check's count, in `video_terminal` (39), `filesystem_protocol` (27),

## Triage, second batch, 2026-10-05

Lane `lane/326-survivors-2`, base `ab0513065`. It added 111 rows (check: 368 triaged, 104 untriaged)
for `video_terminal`, `filesystem_protocol`, `machine_discovery` and `swish`, and **no test**.
Re-running cargo-mutants on each file first showed most keys were already killed on main by tests
landed after the 2026-10-03 run, so 96 rows say that. The other 15 are equivalent (13) or gaps (2).

- `video_terminal`: three byte-disjoint `|` mutants, a sorting-network tie, a `filter(|_| i < n)` whose
  slot is always zero, and the `damage_cell` call in `scroll_damage`, which the drawn-position update
  and `take_damage`'s drawn-versus-now net both cover.
- `filesystem_protocol`: every `<< with >>` survivor is `1 << 0`. Two `<` mutants of the
  compile-time `verb::TABLE` walk are gaps, because `rustc` is that checker (already recorded in
  this milestone's Follow-on).
- `machine_discovery`: `1 << 0` flags, an `RMRR` base and limit that can never be equal, and a
  parity check where `-` and `+` agree.
- `swish`: `command_position` after `<` or `>`, and `cap`'s padding at slot 10, which no preview
  reaches. The padding one becomes live if a slot 10 is ever previewed through `cap`.

**What this says about the instrument.** About 86% of the second batch's keys were stale, killed
between the census and the check. A triage lane should re-run the file before it reads the code.

Those 104 keys stood for 128 mutants in the 2026-10-05 census (1004 survivors); 12 remain, all
equivalent, so the projected count is 1004 less 116, about 888. Projected, not measured. The new
tests also kill `RawQueue::pop8`'s `%` to `+`, which had no row because it predates the inflow window.

- **Six mutants that looked equivalent became kills by writing the code once.** `Note::of` and
  `SubtreeGrantsNote::of` each hand-copied a loop that wrote four-byte words at `at + i`. Every word
  written is under 256 and lands on zeros, so `at - i` produced the same note and no value could
  tell them apart. `put4` is the loop written once, tested with four different bytes. A rung-1 answer
  again: fewer places to be wrong rather than seven arguments to review.
- **A test that checks the bytes cannot see an index.** `pop8` reads `head` only through
  `% RAW_QUEUE_MAX`, so a `head` that grows by a whole ring each pop delivers the same bytes. The new
  test asserts `head < RAW_QUEUE_MAX`.
- **Constants with a sum were the other cluster.** A const assert against a differently spelled
  value pins `supervisor::BUDGET_PAGES`, `abi::virtio::DMA_PHYS_OFFSET` and
  `machine_statistics_protocol::PAGE_BYTES`, the way `login_protocol` already pins its budgets.
- 65 of 104 keys were stale between the 2026-10-05 census and this base, mostly from milestone 637's
  batches. The census runs at its own commit, so a triage lane should still re-run the file first.
