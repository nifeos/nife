# The 2026-08-03 baseline, the calibration, and the recurring patterns

The fixed point every later census is compared against, how its counts were derived, and what the
first run taught. [notes/mutation-testing.md](../mutation-testing.md) carries the current numbers;
this appendix verifies the baseline row.

## The baseline

The machine-readable copy is `.cargo/mutants-baseline.txt`, written by
`script/mutation --save-baseline`. It is what the weekly report diffs against. The table below is
the same numbers with the story attached.

A timeout here is almost always a detected hang, not an undetected bug. The classic case is `+=`
becoming `-=` on a walker's cursor, which loops forever and trips cargo-mutants' auto-timeout. It is
still listed per crate, because a timeout that is not a hang would be invisible inside a merged
"caught" number.

The table is the run of 2026-08-03: 5,551 mutants over 38 host crates, 4,654 caught, 391 missed,
96 timed out and 410 unviable. That is 92.4% of the viable mutants killed. It cost about five and a
half hours at `-j 2` on an 8-core, 16 GiB machine.

Crate names are the ones the run measured. Where one has since changed, the row keeps the measured
spelling, so the number stays traceable to the command that produced it. `asid` is
`address_space_identifier` since 2026-09-18, per §154 (the acronym test is whether the phrase is
spoken).

Read the `missed` column as a worklist, not a score, and as of that run. Every one of those 391 was
triaged afterwards, and the triage commits closed about two hundred of them. So a rerun would
report a smaller number. The table is not restated from a rerun, because the honest way to
re-measure is the weekly workflow, on a machine not also running the triage. What each survivor
became is in [abi to ipc](baseline-survivors-abi-to-ipc.md) and
[grant_plan to swish](baseline-survivors-grant-plan-to-swish.md). Those counts and these measure
two different moments, and both are labeled.

**`killed%` counts a timeout as a kill**, because every one of the 96 was checked by hand and every
one is a detected hang. It is over viable mutants, so `unviable` is excluded from the denominator:
an unviable mutant does not compile, which says nothing about the tests.

Five crates scored 100%: `nifefs`, `dma_validator`, `elf`, `memory_regions` and `bitmap_font`.
The first two are the trust-boundary parsers. They got there the hard way: every one of their 24
first-pass survivors was a real gap that a test then closed. That is the number to compare a crate
against next week.

Four numbers need an asterisk before anyone reads them as quality:

- `video_terminal` at 72.8% and `pci` at 77.3% were untriaged when the run happened. Both are now
  done, and their survivors were overwhelmingly real.
- `intrusive_fifo` at 57.1% is 4 caught of 7 viable. The crate is small enough that one mutant
  moves the percentage nine points.
- `line_editor` at 80.1% is what a terminal looks like when its tests assert what the screen shows
  and never where the cursor is.

### How the numbers were derived

The method matters if you reproduce them. The run was resumed twice: once after an OOM at `-j 4`,
once to finish the tail. So its `caught.txt` holds only what the final pass caught. The earlier
passes' kills are in `previously_caught.txt`, which also carries their unviable mutants, and
reading `caught` off that file would undercount.

Instead the table takes each crate's total from `cargo mutants --list` on the merged tree. It
subtracts missed, timeout, and the union of every pass's unviable, and calls the rest caught.
Three of the 5,551 listed mutants could not be matched to any pass's outcome: two in `glob` and one
in `network_time_protocol`, both crates whose line numbers moved when tests landed. They are counted
as caught, the only place this table guesses.

## Calibration: the exhaustive crates

Milestone 85 (mutation testing over the host crates) predicted that `network_time_protocol` and
`gpt` would score near-perfectly, as a check on the tool. They scored near-perfectly exactly where
their exhaustive method reaches, and the tool showed precisely where that is.

- `network_time_protocol`: 155 of 186 mutants caught on first contact (83%, or 90% of the viable
  ones). Every conversion the sweeps quantify over was mutation-proof. The 17 survivors sat in what
  the sweeps never read. A range constant was tested from one side only, and some accessors no test
  called. A fixture's tiny root delay could not tell `/ 2` from `% 2`. And no rejection test probed
  stratum 15, only 16. Four tests closed them; the rest are equivalents. One was proven equivalent
  by the sweep itself. The 1e9-value round-trip passes under the mutant, because the backward
  conversion's rounding absorbs the forward truncation.
- `gpt`: the same shape with a sharper lesson. The single-byte-corruption sweep proves rejection,
  not rejection for the right reason. Every corrupt header dies at the CRC before the layout checks
  run, so every layout comparison could rot invisibly. One of them (`>` at the backup-array
  boundary) was hiding a real wrong-accept bug, and the mutant fixed it.

So the calibration passed in the way that matters. The tool agreed with the exhaustive suites about
everything they assert, and disagreed only where they assert less than they appear to.

## Survivors and where each one went

Every survivor from the baseline run is accounted for in one of the three buckets of
[the triage rule](../mutation-testing.md#the-triage-rule), crate by crate, in
[abi to ipc](baseline-survivors-abi-to-ipc.md) and
[grant_plan to swish](baseline-survivors-grant-plan-to-swish.md). "Killed by" names the test
written for it. [The ledger](baseline-ledger.md) totals them.

### Patterns that recur, named once

- Bit-constant survivors (`1 << n` becoming `1 >> n`). Every crate that defines a wire format as
  shifted constants had them. The fix is one test pinning the exact values. `1 << 0` mutated to
  `1 >> 0` is the degenerate case: both are 1, so that mutant is equivalent, and is recorded as
  such wherever it appears. `abi` 238, `c_seam` 145 and `capability` 63 had the killable siblings.
- Boundary survivors (`>` becoming `>=` at a length or range check). The tests tried a short value
  and an over-long one, never the exact limit, so the limit itself was never proven legal. The fix
  is a test at the boundary. In one case, `gpt` below, the mutant exposed not a missing test but a
  missing `=`.
- `debug_assert` shielding. A release-mode guard behind a `debug_assert!` of the same condition is
  unobservable under `cargo test`, which runs with debug assertions on. Every input that would reach
  the guard's differing behavior panics first, in both the original and the mutant. Those mutants
  are recorded as equivalent under the harness, not excluded in config, so they stay visible if the
  assertions ever move.
- Single-threaded blindness. Mutants in seqlock and atomic orderings (`clock_protocol`'s `publish`)
  change nothing a single-threaded test can observe. Concurrency claims are argued in the code's
  comments and, where pure, proved. A unit test cannot carry them.

### gpt: one real bug, fourteen missing tests

The `>` to `>=` survivor at `Gpt::parse`'s backup boundary was a genuine wrong-accept.
`block_count - backup_reserved` is the backup array's first block; it is exactly what
`backup_entry_lba` computes. Equality put one usable block inside the backup entry array, where a
partition would overwrite it.

The mutant was the fix: `parse` now refuses equality, and the boundary has a test on both sides.
No test could see the difference before. `real_disks.rs` corrupts one byte at a time, so every
corrupt header dies at the CRC before the layout checks run. And every table `create` makes is
tight on both boundaries. Forging CRC-valid headers with one layout lie each killed the other
fourteen `gpt` survivors (`table.rs`).

This is the asterisk on the calibration: an exhaustive sweep proves *rejection*, not *rejection for
the right reason*. A mutant that weakens check B survives any input that also trips check A.
